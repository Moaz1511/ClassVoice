# 05 — Relational Schema and Authorization

**Product:** ClassVoice  
**Document status:** Locked baseline v1.0  
**Last updated:** 2026-10-27  
**Database:** PostgreSQL 17.11 with Supabase Auth and Storage

## 1. Conventions

- Every ID is a UUID generated by `gen_random_uuid()` unless explicitly noted.
- Every timestamp is `timestamptz` in UTC.
- `created_at` and `updated_at` are present on mutable business tables.
- Audio bytes live in private object storage; `audio_assets.object_key` is only an internal pointer.
- Soft deletion is used for auditable resources; a separate purge worker performs irreversible object deletion.
- `auth.users` is managed by Supabase and is the source of identity truth.
- All tables in the `public` schema have RLS enabled. Service-role workers bypass RLS only through a server-side connection that is never exposed to clients.

Invariant: a voice may transition to `ready` only when it has a primary available `audio_asset`, an approved `model_versions` row, and one non-revoked `voice_consent_records` row. An accepted consent must reference a published canonical statement, use that statement's SHA-256 text hash, and record the accepting actor. Accepted evidence is immutable; a revoked or expired consent record cannot transition back to accepted. Each acceptance appends an `audit_events` row with action `consent.accepted`, actor, statement version, hash, and timestamp.

## 8. RLS model

### 8.1 Helper functions

Create `app` helper functions in a migration owned by the database owner. They must be `security definer`, set a safe `search_path`, and never accept arbitrary SQL. The helpers read `workspace_members` with row security disabled inside the function to avoid recursive policy evaluation.

```sql
create schema if not exists app;

create or replace function app.is_member(target_workspace uuid)
returns boolean
language sql stable security definer set search_path = public
as $$
  select exists (
    select 1 from public.workspace_members wm
    where wm.workspace_id = target_workspace
      and wm.user_id = auth.uid()
  );
$$;

create or replace function app.has_workspace_role(target_workspace uuid, allowed public.workspace_role[])
returns boolean
language sql stable security definer set search_path = public
as $$
  select exists (
    select 1 from public.workspace_members wm
    where wm.workspace_id = target_workspace
      and wm.user_id = auth.uid()
      and wm.role = any(allowed)
  );
$$;
```

The production migration must set `owner` on these functions, revoke `execute` from `anon`, and grant `execute` only to `authenticated` and the API role as appropriate.

### 8.3 Policy rules

The following policy families are required; each migration expands them into explicit `select/insert/update/delete` policies:

```sql
-- Own profile only.
create policy profiles_self_select on public.profiles for select to authenticated
  using (id = auth.uid());
create policy profiles_self_update on public.profiles for update to authenticated
  using (id = auth.uid()) with check (id = auth.uid());

-- Workspace membership is visible to members; only owner/admin can mutate membership.
create policy members_read on public.workspace_members for select to authenticated
  using (app.is_member(workspace_id));
create policy members_admin_write on public.workspace_members for all to authenticated
  using (app.has_workspace_role(workspace_id, array['owner','admin']::public.workspace_role[]))
  with check (app.has_workspace_role(workspace_id, array['owner','admin']::public.workspace_role[]));

-- Workspace-scoped resources.
-- Apply this pattern to voices, consent, assets, samples, projects, jobs, outputs,
-- keys, webhooks, usage, moderation, exports, and audit reads:
create policy resource_member_select on public.voice_profiles for select to authenticated
  using (app.is_member(workspace_id));
create policy resource_editor_write on public.voice_profiles for insert to authenticated
  with check (app.has_workspace_role(workspace_id, array['owner','admin','editor']::public.workspace_role[]));
create policy resource_editor_update on public.voice_profiles for update to authenticated
  using (app.has_workspace_role(workspace_id, array['owner','admin','editor']::public.workspace_role[]))
  with check (app.has_workspace_role(workspace_id, array['owner','admin','editor']::public.workspace_role[]));
```

Additional restrictions:

- `model_versions`: authenticated users may read only `enabled = true`; only the deployment role can insert/update.
- `audio_assets`, `generation_outputs`, `webhook_deliveries`, and `api_keys`: clients may read metadata only through API views or policies; object bytes/secrets are never exposed through SQL.
- `audit_events`: workspace admins can read their workspace; moderators can read all through a separate privileged API path. No client update/delete.
- `usage_events`: workspace admins can read; no client insert/update; workers insert through the API role.
- `moderation_flags`: reporters can read their own report; moderators can manage all; regular members cannot enumerate reports.
- `data_exports`: requester and workspace admins can read; only API worker can update status/object key.
- Any `delete` policy must be explicit and limited to owner/admin or the documented self-service deletion transaction.

### 8.4 Policy matrix (implementation checklist)

The migration must create named policies for every row below; this matrix is the review contract and prevents an accidental default-open table:

| Table | Member read | Editor write | Admin/owner write | Client direct insert |
|---|---|---|---|---|
| `consent_statements` | published/history | no | deployment role | no |
| `profiles` | own row | own safe profile fields | no role escalation | no |
| `workspaces` | member | no | owner/admin | no |
| `workspace_members` | member | no | owner/admin | invite transaction only |
| `voice_profiles` | member | editor | owner/admin | API path only |
| `voice_consent_records` | member, own subject | no | no direct mutation | API/consent transaction only |
| `model_versions` | enabled rows | no | deployment role | no |
| `audio_assets` | member metadata | no | API worker | quarantine API only |
| `voice_samples` | member metadata | editor via voice service | owner/admin | API path only |
| `projects` | member | editor | owner/admin | editor |
| `generation_jobs` | member | creator/editor cancel only | owner/admin | editor/API key scope |
| `generation_outputs` | member metadata | no | API worker | no |
| `api_keys` | owner/admin metadata | no | owner/admin | owner/admin |
| `webhook_endpoints` | owner/admin | no | owner/admin | owner/admin |
| `webhook_deliveries` | owner/admin | no | worker only | no |
| `usage_events` | owner/admin | no | worker only | no |
| `audit_events` | owner/admin | no | worker/system append | no client write/delete |
| `moderation_flags` | reporter own row | no | moderator | authenticated report API |
| `data_exports` | requester/admin | no | API worker | requester/admin |

The `profiles` update policy must be paired with a column privilege/trigger rule that prevents a client from changing `role`, `terms_version`, or `safety_ack_version`. Consent, audit, usage, model, output, and deletion status mutations are server transactions, not arbitrary client updates.

## 9. Auth and request flow

1. User signs in through Supabase Auth.
2. Browser sends the session cookie/access token to Next.js/API.
3. API validates JWT and resolves `auth.uid()` equivalent to `profiles.id`.
4. API resolves `workspace_id` from an explicit path/body field and checks membership plus required role/scope.
5. SQL executes with RLS context; API never trusts a client-supplied owner ID.
6. For generation, API checks voice status, consent status, model allowlist, text limits, rate limit, and idempotency before inserting `generation_jobs`.
7. Worker claims a job, writes outputs/assets, and emits an audit event; clients poll or receive a signed webhook.
8. Signed download URL is minted only after a fresh authorization check.

## 10. Required database tests

- A user cannot select, update, or delete another workspace’s voice, project, asset, job, key, webhook, or export.
- A viewer cannot create a voice or generation job.
- A revoked voice fails generation even when a stale client has its ID.
- A model not enabled or not license-approved cannot be selected.
- A duplicate `(workspace_id, idempotency_key)` returns the original job, never a second job.
- Deleting a voice eventually deletes its samples, consent evidence, embeddings, and derived outputs while preserving a minimal audit tombstone.
- `anon` cannot read any private table.
- An accepted consent must use a published statement version and matching text hash, records the accepting actor, emits one `consent.accepted` audit event, and cannot be changed back to accepted after revocation/expiry.
